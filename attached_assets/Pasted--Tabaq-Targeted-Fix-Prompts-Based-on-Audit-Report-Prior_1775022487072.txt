## FIX 3 — Fix Partial Voucher / Wallet Balance

```
In the existing codebase, find the wallet or voucher balance deduction logic.

The current implementation deducts the full voucher value even when the order total is less than the voucher balance, leaving no remainder for future use.

Task:
1. Find where voucher/wallet balance is deducted during payment.
2. Fix the deduction to use: amount_to_deduct = MIN(voucher_balance, order_total)
3. The remaining balance = voucher_balance - amount_to_deduct
4. Update the voucher/wallet record with the remaining balance (not zero).
5. On the payment/invoice record, store: voucher_amount_used and voucher_remaining_after.
6. If remaining balance = 0, mark the voucher as fully_used. Otherwise keep it active.

This is a single arithmetic fix. Change only the deduction logic.
Do not change how vouchers are created or validated.
```

## FIX 8 — Membership Lifecycle State Machine

```
In the existing codebase, find the membership status management code.

Membership status transitions are likely ad hoc — status is set directly without validation.

Task:
1. Find where membership status is updated across the codebase.
2. Create a single function: transitionMembershipStatus(membership_uid, new_status, reason?, actor_uid?)
3. Enforce these allowed transitions only:
   PENDING    → ACTIVE (payment succeeded)
   PENDING    → CANCELLED (user cancelled before first payment)
   ACTIVE     → SUSPENDED (payment failed after retries)
   ACTIVE     → CANCELLED (user requested cancellation)
   ACTIVE     → EXPIRED (end_date passed, no renewal)
   SUSPENDED  → ACTIVE (payment recovered)
   SUSPENDED  → CANCELLED (user cancelled while suspended)
   SUSPENDED  → EXPIRED (end_date passed while suspended)
   Any other transition → throw an error with clear message

4. Replace all direct status assignments in the codebase with calls to this function.
5. Every transition must write an entry to the audit_log (or equivalent existing log table):
   entity_type=MEMBERSHIP, entity_uid, old_status, new_status, reason, actor_uid, timestamp.

This is a refactor of existing code, not new functionality.
```

## FIX 9 — Order Status Management

```
In the existing codebase, find all places where order status is changed.

Order status is likely updated in multiple places without a central state machine, causing potential inconsistencies.

Task:
1. Map all current order status values used in the codebase.
2. Create a single function: transitionOrderStatus(order_uid, new_status, metadata?)
3. Define and enforce the allowed state machine:
   PENDING     → CONFIRMED (payment received)
   PENDING     → CANCELLED (payment failed or user cancelled)
   CONFIRMED   → PREPARING (restaurant/supplier accepted)
   CONFIRMED   → CANCELLED (supplier rejected — triggers full refund)
   PREPARING   → READY / DISPATCHED (depending on order type)
   READY       → COMPLETED (customer received)
   DISPATCHED  → COMPLETED (delivery confirmed)
   COMPLETED   → DISPUTED (customer raised dispute)
   Any cancelled or completed order → no further transitions allowed

4. On CONFIRMED: trigger invoice creation (Fix 1) if not already done.
5. On COMPLETED: move pending points to redeemable balance.
6. On CANCELLED (after payment): trigger refund flow automatically.
7. Replace all direct order status updates across the codebase with this function.
8. Log every transition to audit_log.

Do not change the order data model. Only centralize the transition logic.
```
