Based on the audit, harden the existing email+password and phone+OTP flows.
Do not rewrite them. Fix only what is weak or missing.

PHONE + OTP FLOW — check and fix each point:
1. OTP generation: must be 6 digits, cryptographically random (use crypto.randomInt)
   If currently using Math.random() — replace it. Math.random() is not secure.
2. OTP storage: must be hashed (SHA-256) before storing in DB, never plain text
3. OTP expiry: must be exactly 5 minutes from generation. Enforce on verify.
4. OTP attempts: max 3 wrong attempts per OTP → mark OTP as void, require resend
5. OTP resend rate: max 1 resend per 60 seconds per phone number (enforce via Redis key)
6. OTP table/column: ensure fields exist: otp_hash, expires_at, attempts, is_used, phone
7. Phone format: validate and normalize to E.164 format (+966XXXXXXXXX) before storing
8. On successful OTP verify: mark OTP as is_used=true immediately (prevent replay)

EMAIL + PASSWORD FLOW — check and fix each point:
1. Password hashing: must use bcrypt with cost factor 12 minimum
   If cost factor < 12 — update the hash generation (existing hashes still work on verify)
2. Password strength: enforce on registration: min 8 chars, 1 uppercase, 1 number
   Return specific error: PASSWORD_TOO_WEAK with requirements list
3. Email format: validate with regex before any DB operation
4. Email uniqueness: must be enforced at DB level (unique index) AND at application level
   Return specific error: EMAIL_ALREADY_EXISTS (not a generic 500)
5. Email verification: if not implemented, add:
   On registration → generate a 6-digit email OTP → send via existing email service
   User must verify email before first login is allowed
   Add email_verified boolean column if missing

FAILED LOGIN PROTECTION (apply to both phone and email):
- Track failed_login_count on user record
- After 5 consecutive failures: set locked_until = NOW() + 15 minutes
- On every login attempt: check locked_until first, return ACCOUNT_LOCKED with retry_after
- On successful login: reset failed_login_count to 0

JWT HARDENING:
- Access token expiry: must be 15 minutes (not longer)
- Refresh token expiry: 30 days
- Refresh token must be stored in DB with: token_hash, user_uid, device_info, expires_at, is_revoked
- On refresh: verify token exists in DB and is not revoked, then rotate (issue new, revoke old)
- Add jti (JWT ID) claim to access token for future revocation support
- JWT payload must include at minimum: sub (user_uid), type, role, iat, exp, jti

USER UID:
- If users currently have sequential integer IDs or plain UUIDs:
  Add a user_uid column with format USR-[YEAR]-[TIMESTAMP]-[8CHARS]
  Generate for all existing users, add unique constraint
  Keep the original ID column — do not remove it
  All new JWT tokens must use user_uid in the sub claim

Do not change any route paths. Do not change response formats unless they are wrong.
